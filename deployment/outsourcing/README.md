# Точечная публикация страницы «Аутсорсинг ПТО»

Пакет изменяет только ресурс `autsorsing-pto/` контекста `web`. Ни целиком БД, ни архив сайта, ни localhost-конфиги и секреты не переносить. Общие шаблоны, формы, CSS, CRM-сниппеты, региональные страницы и настройки PHP не заменяются.

## Состав

Восемь постоянных файлов: отдельный статический шаблон, три статических чанка открытых форм и четыре изображения. Регистрация выполняется в штатных таблицах MODX, с копированием привязок TV исходного шаблона. ID ресурса и исходного шаблона определяются на целевом сайте, а не берутся из локальной БД. Попап остаётся общим `footer_new` / `#form_up` / `form_tpl1`.

`deploy.php` использует PHP CLI 7.3+, PDO и установленный MODX. Проверенный для этого хостинга путь CLI — `/usr/local/bin/php7.3`; это не команда переключения веб-PHP. Код шаблонов — HTML/MODX, без нового PHP веб-обработчика. Нельзя считать CLI-версию самостоятельным доказательством текущей веб-версии.

## Подготовка без изменения хостинга

Из корня проекта: `node deployment/outsourcing/prepare.mjs audit-host`, затем `node deployment/outsourcing/prepare.mjs build`. Первая команда выполняет исключительно SELECT и чтение файлов по SSH, без загрузки файлов на сервер. Она сверяет текущую страницу, исходный шаблон, TV и зависимости форм. Вторая создаёт пакет в игнорируемом `dist/`. Повторное создание поверх пакета запрещено.

Неизвестные изменения страницы/общих зависимостей или занятые имена/пути блокируют установку. Для новой проверки не редактировать разрешённые хэши вручную: сначала выяснить изменения, затем собрать новую проверенную версию.

## Порядок публикации — только после отдельного разрешения

1. Снять свежие полные резервные копии файлов и БД хостинга и проверить целостность обоих архивов. Сохранить вне `public_html`; не заменять ими локальную версию.
2. Проверить локальные контрольные суммы пакета и архива. Загрузить и распаковать отдельный пакет вне `public_html` под владельцем сайта, не root. Повторно сверить контрольные суммы после загрузки. Никаких вебхуков в пакете нет.
3. Выполнить `/usr/local/bin/php7.3 deploy.php inspect /absolute/public_html`. Это режим чтения, без очистки кэша и записи в MODX. При любой разнице с подготовленной базой остановиться и разобраться.
4. После успешной проверки резервных копий создать рядом с `release.json` приватный `backup-confirmation.json` с `releaseId`, `targetRoot`, `verifiedUtc` (UTC), `fullFilesBackupVerified: true`, `fullDatabaseBackupVerified: true`, `filesSha256`, `databaseSha256`. Хэши брать только из фактически проверенных архивов; срок подтверждения — 24 часа. Публикация без этого подтверждения блокируется.
5. Выполнить `/usr/local/bin/php7.3 deploy.php apply /absolute/public_html`. Скрипт сначала сохраняет приватный снимок затрагиваемой записи и связей. Затем устанавливает новые файлы, новый шаблон и чанки; только в самом конце переключает шаблон одного ресурса. Журнал: `<родитель public_html>/.isipto-release-backups/<releaseId>/state.json`, не доступен по HTTP. При ошибке выполняется компенсирующий откат, в том числе для старых таблиц MyISAM. Проверить журнал при любом сбое.
6. Проверить HTTP, заголовки, внутренние ссылки, картинки, обе открытые расчётные формы, нижнюю форму и штатный попап на десктопе/мобильном. Проверить главную и региональные страницы. С отдельно согласованными данными отправить контрольные заявки из попапа и открытой формы, обязательно с чекбоксом согласия. В CRM подтвердить отсутствие дублей, воронку «ИД Отдел продаж» (31) и ответственную Яну Черную (3280). Страница «Спасибо» не доказывает доставку.
7. При сбое выполнить `/usr/local/bin/php7.3 deploy.php rollback /absolute/public_html`. Восстанавливается только прежняя привязка шаблона целевой страницы; удаляются лишь созданные этим пакетом записи и файлы. Заявки и прочая БД не откатываются. Если затронутые элементы после релиза менялись или новый шаблон используется другой страницей, автоматический откат откажется — нужна ручная сверка с журналом.

Публикация не считается законченной без проверки CRM. Команды подготовки и репетиции реальные заявки не отправляют.

Перед отдельной публикацией повторить `node deployment/outsourcing/prepare.mjs recheck-host`: команда только читает хостинг и откажет, если страница/шаблон/TV/формы изменились после подготовки. `node deployment/outsourcing/verify-package.mjs` проверяет целостность пакета, отсутствие незапланированных файлов и совпадение с локальной страницей; для PHP-линтинга требуется запущенный изолированный стенд. Передача самого пакета на сервер и `apply` этими командами не выполняются.

## Изолированная репетиция

При недостатке локального места `publish.mjs start-after-rollback` начинает новый цикл только после подтверждённого отката предыдущего, сохраняя прежний журнал. Команды `backup-remote` и `verify-backups` создают и проверяют полные архивы в новой приватной папке `/home/i/idealstroy/_codex_backups/<releaseId>` (вне `public_html`, каталог 0700, архивы 0600). Локально остаются только контрольные суммы и отчёты. Старые архивы не удаляются. SQL выгружается без блокировок и импорта, поэтому для MyISAM это горячая, а не атомарная копия; точечный установщик дополнительно сохраняет затрагиваемые записи и проверяет отсутствие параллельных изменений. Контрольные CRM-заявки фильтруются по времени начала текущего цикла публикации.

После уже проверенного общего CRM-исправления допускается `node deployment/outsourcing/prepare.mjs refresh-after-crm-fix`, затем `build` и `node deployment/outsourcing/verify-package.mjs --host-php73-lint`. Обновление контрольной базы разрешается только для точного хэша опубликованного CRM-исправления, при отсутствии прочих расхождений. Установщик и все восемь файлов страницы должны остаться байт-в-байт прежними. В этом случае сохраняется ссылка на предыдущую репетицию, а не выдаётся утверждение о новой репетиции. SSH-линт использует только stdin и ничего не записывает на сервер. Перед публикацией нужны свежие резервные копии; старые архивы не становятся свежими от пересборки пакета.

Допускается отдельная копия пакета с фактической базой изолированного стенда. Флаг `--offline-rehearsal` работает исключительно с `database_server=isipto-direct-rehearsal-db` и корнем `/var/www/html`; на хостинге запрещён программной проверкой. Реальный вебхук не подключать, внешнюю сеть не включать. Боевой архив при репетиции не модифицировать.
