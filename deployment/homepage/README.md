# Точечный релиз главной — 21 октября 2026

> Историческая инструкция для первоначальной публикации. После перехода форм на прямой Битрикс24 использовать `DIRECT-RELEASE.md`, `build-direct-release.mjs` и `deploy-direct.php`. Старый пакет из семи файлов не включает новую CRM-интеграцию и не подходит для её публикации.

Это пакет подготовки, а не разрешение автоматически публиковать сайт. Рабочая БД, общие формы и другие страницы в пакет не включены. Главная локально: http://localhost:3000/. Тестовый URL удалён и не восстанавливается.

## Состав

`payload/` содержит ровно 7 файлов: изолированный шаблон главной, чанк отзывов, CSS, JS и 3 используемых изображения. `manifest.json` содержит размеры и SHA256. `release-spec.json` описывает элементы MODX и зависимости по именам, а не по локальным ID.

Не переносить корневые статические прототипы проекта, index.php, .htaccess, Docker, config.core.php, core/config, sessions, cache, локальный дамп БД, .ssh, .agents, Semantic core и _backups. Нельзя заливать весь репозиторий поверх сайта.

## 1. Проверить пакет и окружение

Сверить SHA256 ZIP с соседним .sha256. Распаковать на хостинге ВНЕ публичного каталога. От имени пользователя сайта выполнить только проверку:

```sh
php /absolute/release/preflight.php /absolute/site/public_html
```

Проверка CLI-only, не устанавливает релиз и не отправляет заявки. Нулевой exit-code подтверждает наличие зависимостей и целостность payload, но не доставку CRM, дизайн на другом окружении или свежесть бэкапа. Скрипт рассчитан на PHP 5.6+ и MODX Revolution. Не размещать инструменты релиза в web-каталоге.

Уточнение аудита 22.10.2026: HTTP-ответ домена сообщает PHP/7.3.33, тогда как SSH-команда `php -v` запускает PHP 5.6.40 CLI. Это разные обработчики. Исходный серверный index.php уже содержит `??` и на PHP 5.6 не разбирается. Не переключать веб-PHP ради релиза; совместимость самого preflight с 5.6 не означает совместимость сайта с 5.6. Итоги проверки — docs/hosting-audit-20261022.md в локальном проекте.

## 2. Сделать свежий бэкап рабочего сайта

Сохранить вне публичного каталога файлы и полный дамп текущей рабочей БД штатными средствами хостинга. Проверить, что архив и дамп читаются. Для MyISAM --single-transaction НЕ гарантирует согласованность: согласовать способ резервирования с хостингом, не вводить самостоятельно блокировки рабочего сайта.

Отдельно записать фактический site_start контекста web, ID и имя его текущего шаблона, editedon, связи TV, метаданные, настройки контекста. Сохранить предыдущие версии любых совпадающих файлов payload. Локальные номера 3075/84/134 не использовать на сервере как константы.

## 3. Перенести файлы без переключения главной

Через SFTP/SSH перенести ТОЛЬКО 7 файлов payload с сохранением относительных путей. Права и владельца установить по существующим файлам сайта; не использовать 777. Перед заменой существующего одноимённого файла сохранить его копию. Проверить SHA256 загруженных файлов. Общие CSS, header_new, footer_new, index_new.html, формы и CRM-хуки не заменять локальными версиями.

## 4. Зарегистрировать элементы штатно через MODX

В менеджере создать отдельный статический чанк home_solution_review, указать assets/templates/home_solution_review.html и источник файловой системы с базой в корне сайта (локальный source=0 — ориентир, фактический источник проверить на хостинге).

Создать отдельный статический шаблон «Главная — управляемая служба ПТО», файл assets/templates/home_solution.html, тот же корректный источник. Если элемент с таким именем/путём уже существует — проверить, что он относится к этому релизу, не перезаписывать неизвестный элемент.

Скопировать ВСЕ связи TV и их порядок из фактического исходного шаблона главной. В текущей локальной версии это canonical, email_to, h1, og_description, og_site_name, og_title, og_type, og_url, seodescription, seokeywords, seotitle. Имена на хостинге проверять по исходному шаблону. Значения TV, документы, отзывы, проекты, блог, настройки и ресурсы не импортировать из локальной БД.

## 5. Контрольная точка перед активацией

Подтвердить свежий проверенный бэкап, успешный preflight, целостность файлов, готовность отката и согласованное окно публикации. Доставка заявки в Roistat/Битрикс24 ещё не подтверждена. До публикации выполнить разрешённый владельцем сквозной тест на защищённом staging с нужными настройками интеграции либо согласовать контролируемую проверку сразу после переключения и немедленный откат при сбое. Не отправлять тесты без разрешения и не отключать защиту форм.

Риск существующего CRM-хука: он не анализирует ответ Roistat и может показать успех без подтверждённой доставки. Подробности в form-delivery-audit.md. Хук этим релизом не исправляется.

## 6. Переключить только главную

Только после отдельного разрешения владельца назначить новый шаблон фактическому главному ресурсу web. Не менять URL/alias, site_start, published, контент других страниц, SEO/TV и региональные главные. Сохранить через MODX, обновив editedon для LastModified. Очистить кэш штатно, не удалять все каталоги вручную. При CLI выполнять действия пользователем сайта, не root.

Проверить главную без кеша: HTTP 200, единственный H1, Title/Description/canonical, оригинальные меню, ссылки, изображения, формы, закрепление хэдера, мобильный режим, отсутствие [[...]] и локальных адресов в HTML. Проверить главные коммерческие страницы, региональную главную и блог. Исходная локальная 403 на /vedenie-id/ — отдельно известное состояние, не новая ошибка релиза; ссылка обновлённого контента использует /index.php?q=vedenie-id/.

Отдельно по согласованию отправить маркированную заявку из попапа и нижней формы, найти обе в Roistat И Битрикс24, проверить телефон, страницу, причину, ответственного, воронку и отсутствие дублей. Уведомление интерфейса или запись в FormIt не считать доказательством доставки. Не менять настройки аналитики, ключи и CAPTCHA на основании одного локального теста.

## 7. Откат

При проблеме вернуть главному ресурсу записанный в шаге 2 исходный шаблон, сохранить с обновлением editedon и очистить штатный кэш. Это возвращает прежнюю страницу без восстановления всей БД и потери новых заявок. Вернуть прежние версии файлов, если они существовали до переноса. Новые файлы/элементы удалять только после проверки отсутствия ссылок и при сохранённой копии. Не импортировать полный старый дамп поверх свежих лидов и изменений сайта.

## Повторная сборка локально

Из корня проекта, PowerShell 7:

```powershell
pwsh -File scripts/build-homepage-release.ps1
```

Каждая сборка получает отдельное имя в игнорируемом dist/. Исходные файлы остаются в modx-isipto; архив не содержит секретов из конфигурации или CRM-хуков.
